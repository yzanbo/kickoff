# Kickoff 要件定義書（ドラフト v0.1）

> ステータス: レビュー中。「8. 未決事項」が決まりしだい v0.2 に更新する。

## 1. 背景と目的

個人で Web アプリを新規開発するときに、AI エージェント（Claude Code / Codex）を使って、アイデアからデプロイまでをスムーズに進めたい。

既存のツールは、どれも会話（セッション）が中心になっている。そのため「このアプリは今どの段階か」「要件は何だったか」「次に何をやるか」が会話の中に散らばり、開発の流れ全体を追いにくい。

Kickoff は**開発の流れを軸にして**、AI との会話をその流れの中に位置づける。

- 開いた瞬間に、プロジェクトの**現在地**と**次にやること**がわかる
- 要件・タスク・会話・成果物が 1 か所でつながっている
- AI がやったことを、人が要所でレビュー・承認できる

## 2. 利用者と利用環境

| 項目 | 内容 |
|---|---|
| 利用者 | 自分 1 人（配布しない） |
| 環境 | macOS（Apple Silicon）のデスクトップアプリ |
| スマホ | 外出先から操作したい。v1 はブラウザから使い、将来はネイティブアプリにする |
| AI エージェント | Claude Code（Agent SDK）に先に対応し、次に Codex。Gemini は検討中 |
| 認証 | 各 CLI のログイン（Claude / ChatGPT のサブスクリプション）をそのまま使う。API キーや従量課金は使わない |

## 3. 対象とする開発

- **新規の Web アプリ開発**（既存アプリの取り込みは v1 の対象外）
- デプロイ先: 未決（→ 8. 未決事項）

## 4. 想定する利用の流れ

1. **構想**: アイデアを数行書いて、新規プロジェクトを作る（フォルダ作成と `git init` まで自動）
2. **要件定義**: AI と壁打ちする。AI が選択肢付きで質問し、人が答える。最後に要件定義書ができて、人が確定する
3. **技術選定・雛形**: AI が技術スタックを提案し、人が確定する。AI が雛形を作る
4. **タスク分解**: AI が要件を受け入れ基準付きのタスクに分解する。人が確認・調整する
5. **実装**: AI がタスクごとに実装する。複数のタスクを並列に進める（タスクごとにブランチで分離）
6. **レビュー**: 人が差分を見て OK ならマージする。直してほしければコメントを付けて差し戻す
7. **テスト・動作確認**: AI がテストを作って実行する。人はアプリ内からローカルでプレビューして確認する
8. **デプロイ**: 人が承認すると AI がデプロイし、URL とログを記録する
9. **改善**: 機能追加やバグを起票し、5 に戻る

外出中はスマホで次のことをする。

- AI の承認依頼・質問に答える
- 進み具合を確認する
- 次の指示を出す

## 5. 機能要件

優先度: **Must** = v1 に必須 / **Should** = v1 に入れたい / **Could** = 将来

### 5.1 プロジェクト

| 優先度 | 機能 |
|---|---|
| Must | 新規作成（名前・アイデア・保存先を指定 → フォルダ作成と `git init`） |
| Must | 一覧（各プロジェクトの現在のフェーズ・進捗・承認待ちの件数） |
| Must | 「現在地」と「次にやること」の表示（例:「要件定義書の確定待ち」「レビュー待ち 2 件」） |
| Could | 既存フォルダの取り込み |

### 5.2 フェーズ管理

| 優先度 | 機能 |
|---|---|
| Must | 要件定義 → 実装 → テスト → デプロイ の 4 フェーズ（技術選定の扱いは 8. 未決事項） |
| Must | フェーズの区切りに人の確定（ゲート）を置く（例: 要件定義書を確定するとタスク分解に進む） |
| Should | フェーズごとに AI の権限を変える（要件定義は読み取りのみ、デプロイは全コマンド承認制 など） |

### 5.3 要件定義

| 優先度 | 機能 |
|---|---|
| Must | AI とのチャットで要件を詰める。AI の質問に選択肢か自由記述で答える |
| Must | 要件定義書を作って `docs/requirements.md` に保存する（git で版管理） |
| Must | 確定後に AI がタスクに分解し、人が編集・承認する |

### 5.4 タスク

| 優先度 | 機能 |
|---|---|
| Must | ステータス: TODO / 実行中 / レビュー待ち / 完了 / ブロック |
| Must | 人も AI も起票できる（AI が起票したものは区別して表示する） |
| Must | タイトル・内容・受け入れ基準・優先度 |
| Could | タスク間の依存関係 |

### 5.5 エージェント実行（セッション）

| 優先度 | 機能 |
|---|---|
| Must | タスクからエージェントを起動する。チャットで追加の指示を出して会話を続けられる |
| Must | 実行ログをリアルタイムで表示する（AI の発言・ツールの使用・コマンドの結果） |
| Must | 承認カード（許可 / 常に許可 / 拒否）と、AI の質問への回答 |
| Must | 中断と再開（アプリを再起動しても続きから再開できる） |
| Should | 複数タスクの並列実行（同時実行数に上限を設ける） |
| Should | タスクごとに git worktree とブランチで作業を分離する |
| Could | タスクごとにプロバイダー（Claude / Codex）を選ぶ |

### 5.6 レビュー

| 優先度 | 機能 |
|---|---|
| Must | 変更差分をファイルごとに表示する |
| Must | 承認したらマージし、タスクを完了にする |
| Must | 差し戻すとき、コメントを AI に送って再実行する |

### 5.7 テスト・動作確認

| 優先度 | 機能 |
|---|---|
| Must | AI がテストを作って実行し、結果をレポートにまとめる |
| Must | 不具合が見つかったらバグタスクとして起票する |
| Should | 開発サーバーをアプリから起動・停止して、ブラウザでプレビューする |

### 5.8 デプロイ

| 優先度 | 機能 |
|---|---|
| Must | デプロイ先と手順の設定 |
| Must | 事前チェック（テスト合格・未マージの変更なし）→ 人の承認 → 実行 → URL とログを記録 |

### 5.9 スマホ連携

| 優先度 | 機能 |
|---|---|
| Must | 同じ Wi-Fi か Tailscale 経由で、スマホのブラウザから操作する（トークン認証・QR でペアリング） |
| Must | スマホでできること: 承認・質問への回答、進捗とログの確認、タスクの作成・実行の指示 |
| Should | 通知（承認待ち・完了・失敗）。v1 は macOS の通知と ntfy（任意） |
| Could | ネイティブアプリ（デスクトップと同じ API を使う）とプッシュ通知 |

### 5.10 設定

| 優先度 | 機能 |
|---|---|
| Must | プロバイダーのログイン状態の表示とモデルの選択 |
| Must | 同時実行数、通知、スマホ連携の on / off |

## 6. 非機能要件

- **ローカル完結**: データは Mac 内（SQLite）に置く。外部に送るのは AI プロバイダーへの通信と、任意で有効にする通知だけ
- **セキュリティ**: 外部からのアクセスはトークン必須。デプロイやリポジトリ外への書き込みなど、影響の大きい操作は承認制
- **使用量**: サブスクリプションの上限を意識する（同時実行数の上限、API 換算の推定コストを表示）
- **拡張性**: プロバイダーを追加しやすくする。HTTP API はデスクトップの画面・スマホのブラウザ・将来のネイティブアプリで共通にする
- **復旧性**: アプリが落ちても、中断した実行を続きから再開できる

## 7. 画面構成（案）

```
┌────────────┬─────────────────────────────────────────────┐
│ プロジェクト │ [要件定義]━[実装]━[テスト]━[デプロイ]  ← 現在地  │
│  ・App A ●2 │ ┌ 次にやること ──────────────────────────┐ │
│  ・App B    │ │ レビュー待ち 2 件 / AI からの質問 1 件  │ │
│            │ └──────────────────────────────────────┘ │
│ ＋ 新規     │ [タスク] [セッション] [成果物] [設定]          │
│            │  TODO │ 実行中 │ レビュー待ち │ 完了          │
│ ⚙ 設定     │  ...  │  ...   │   ...       │ ...           │
└────────────┴─────────────────────────────────────────────┘
```

- セッション（チャット）はタスクから開く。右側のパネルかタブに表示する
- 承認依頼と AI からの質問は、どの画面にいても目立つ位置に出す
- スマホでは同じ画面を縦 1 列にして表示する

## 8. 未決事項

1. **デプロイ先**: Vercel を標準にしてよいか（Web アプリで一般的。GitHub 連携が前提になることが多い）
2. **技術スタックの既定値**: 毎回 AI と相談して決めるか、既定のスタック（例: Next.js + TypeScript + Tailwind）を持つか
3. **フェーズ構成**: 技術選定と雛形づくりを要件定義に含めるか、「設計」フェーズとして独立させるか
4. **マージ先**: レビュー後はローカルの main にマージするか、GitHub に push して PR を作るか
5. **GitHub 連携**: リポジトリの作成や push を v1 に含めるか
6. **v1 の範囲**: 並列実行と worktree による分離（5.5 の Should）を v1 に含めるか
