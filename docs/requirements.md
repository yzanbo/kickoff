## 0. 用語

| 用語 | 意味 |
|---|---|
| **Kickoff** | この文書で定義するアプリ本体。**Mac のデスクトップアプリ**（Electron） |
| **開発対象アプリ** | Kickoff を使って開発するアプリ。種類は限定しない（Web / スマホ / デスクトップ など） |

3 章以降の「技術スタック」「デプロイ先」は、開発対象アプリについての話であり、Kickoff 本体についての話ではない。

## 1. 背景と目的

アプリを新規開発するときに、AI エージェント（Claude Code / Codex）を使って、アイデアからデプロイまでをスムーズに進めたい。

既存のツールは、どれも会話（セッション）が中心になっている。そのため「このアプリは今どの段階か」「要件は何だったか」「次に何をやるか」が会話の中に散らばり、開発の流れ全体を追いにくい。

Kickoff は**チャット中心**のツールにする。プロジェクトの中に、作業場所（git のワークツリー・ブランチ）・グループ・状態で分けたチャットを並べ、AI と話しながら並行して進める。要件定義書などの文書は、リポジトリのファイル（`docs/` など）として持ち、git で版管理する。

- 開いた瞬間に、どのチャットが作業中・回答待ちかがわかる
- プロジェクトのチャット・作業場所（ブランチ）・差分・PR が 1 か所でつながっている
- AI がやったことを、人が要所でレビュー・承認できる

## 2. 利用者と利用環境

| 項目 | 内容 |
|---|---|
| 利用者 | アプリの開発者 |
| 環境 | macOS（Apple Silicon）のデスクトップアプリ |
| スマホ | 外出先から操作したい。v1 はブラウザから使い、将来はネイティブアプリにする |
| AI エージェント | Claude Code（Agent SDK）に先に対応し、次に Codex。Gemini は検討中 |
| 認証 | 各 CLI のログイン（Claude / ChatGPT のサブスクリプション）をそのまま使う。API キーや従量課金は使わない |

## 3. 対象とする開発

- **アプリの新規開発**と、**開発途中の既存プロジェクトの取り込み**
- **開発対象アプリの種類は限定しない**。Web・スマホ・デスクトップなど、どの種類でも同じ流れで進められるようにする
- 技術スタックとデプロイ先・リリース方法は、プロジェクトごとに要件定義の中で AI と決める（Kickoff 側で特定のサービスに固定しない）

## 4. 想定する利用の流れ

決まった順番はなく、必要なときにチャットを立てて進める。典型的には次のようになる。

1. **構想**: アイデアを数行書いて、新規プロジェクトを作る（または既存フォルダを取り込む）
2. **要件を詰める**: チャットで AI と壁打ちする。AI が選択肢付きで質問し、人が答える。AI が要件定義書（技術スタック・デプロイ方法を含む）を `docs/requirements.md` にまとめる
3. **実装**: 作業ごとにワークツリー（ブランチ）を作ってチャットを立て、AI が実装する。複数のチャットを並列に進める
4. **レビュー**: 人が差分を見て、OK ならブランチを GitHub に push して PR を作る（マージは GitHub 上か、Kickoff の GitHub タブで行う。「5.11 GitHub」）。直してほしければチャットで伝える
5. **テスト・動作確認**: チャットで AI にテストを作らせて実行する。人はアプリ内からローカルでプレビューして確認する
6. **デプロイ**: チャットで、人が承認しながら AI がデプロイする
7. **改善**: 機能追加やバグの修正は、新しいチャットを立てて進める

外出中はスマホで次のことをする。

- AI の承認依頼・質問に答える
- 進み具合を確認する
- 次の指示を出す

## 5. 機能要件

優先度: **Must** = v1 に必須 / **Should** = v1 に入れたい / **Could** = 将来

### 5.1 プロジェクト

| 優先度 | 機能 |
|---|---|
| Must | 新規作成（名前・アイデア・保存先を指定 → フォルダ作成と `git init`） |
| Must | 一覧（作業中・回答待ち・未読のチャット数） |
| Must | 回答待ち・作業中のチャットがひと目で分かる表示 |
| Must | 既存フォルダの取り込み（git 未管理なら同意のうえ初期化。登録済みのフォルダは重複登録しない） |

### 5.2 チャット

| 優先度 | 機能 |
|---|---|
| Must | サイドバーは プロジェクト → チャット の 2 段。チャットには状態と作業場所（ブランチ）の印を付ける |
| Should | サイドバーのプロジェクトに、作業中・回答待ち・未読のチャット数を出す（閉じていても分かる）。プロジェクトは最近動いた順にも並べられる。右クリックで、プロジェクトに対するすべての操作を出す |
| Should | サイドバーで、要対応（回答待ち・エラー・未読）のチャットだけに絞れる。チャットをプロジェクトのいちばん上に固定できる。チャットを 1 行で詰めて出せる |
| Should | パネルのタブをグループ別にまとめているとき、グループごとにタブの列に出すか選べる（No Group は除く）。チャットのないグループを自動で隠すかも選べる |
| Should | プロジェクトのタブをドラッグで並べ替えられる（ボード・チャット / ファイル・検索・変更はまとまりごと動き、まとまりの中では 1 つずつ並べ替える。右クリックで元の並びに戻せる） |
| Should | サイドバーのチャットを「アーカイブ済み」へドラッグしてアーカイブできる（右クリックと同じく、必ず確認のダイアログを出す） |
| Should | プロジェクトを上に固定（ピン留め）できる。使っていないプロジェクトはアーカイブでき、サイドバー・切り替え・全プロジェクトの画面に出なくなる（見出しの名前のメニューの「アーカイブ済み」から開いて戻せる。サイドバーでは、閉じた「アーカイブしたプロジェクト」を開くと出る） |
| Must | プロジェクトの「＋」（⌘N）で新しいチャットを始める。チャットごとに状態（作業中・回答待ち・完了など）が見える |
| Must | プロジェクト画面はタブ（ボード / チャット / ファイル / 検索 / 変更 / 履歴 / メモ。グループはボードの中の切り替え）。プロジェクトの設定は名前の横の「編集」から開く。チャットは作業場所・アーカイブ・名前で絞り込める |
| Should | 自分で作ったグループでチャットをまとめられる（サイドバー・ボードの段・全プロジェクトのボードのグループの列） |
| Should | AI の返答のストリーミング表示、ツール実行のまとめ表示と差分表示、チャット名の自動生成、⌘K でチャット・プロジェクトを検索、やり取りを全文検索、⌘⇧F でプロジェクトのファイルの中を検索、⌘F で開いているページ（チャット・ファイル・差分・メモなど）の中を検索 |
| Should | 発言（選んだ文）を右クリックして「新しい子チャットで聞く」で、横道の質問を別のチャット（子チャット）で聞ける。会話を引き継ぐか選べ（初めは引き継ぐ）、親は作業を続けられる。子チャットは一覧に出さず親の中にだけ置き（サイドバーでは親の下に数と開閉）、孫・ひ孫も作れる。答えが来ても開かずに通知し、押すと親のチャットの右の欄（初め）か別ウィンドウ（設定で選ぶ）で開く。別ウィンドウの最小化は閉じ方を聞かずに閉じて親に戻り、タブの ×・ウィンドウの ✕ はチャットの ✕ と同じく閉じ方（表示だけ消す・アーカイブ・削除）を選ぶ。答えは「親チャットに渡す」で親の入力欄に入れられる。入力欄の上の子チャットの一覧では、アーカイブしたものをサブエージェントと同じく「アーカイブ済み」として出し、戻せる。行から削除もできる |
| Should | よく送る指示を定型文として持ち、チャット欄の上の帯（入りきらなければ横にスクロール）から押すだけで入力欄に入れられる（⌘クリック・右クリックですぐ送る）。定型文は共通かプロジェクトだけかを選べ、帯の「一覧」で絞り込んで選べる。すべての定型文は設定で、そのプロジェクトのものはプロジェクトの設定・帯の「定型文を管理」で足す・直す・並べ替える |
| Must | 関門（確定ボタンで次へ進む）は設けない。いつでも自由にチャットできる |
| Must | どのチャットも AI の役割と権限は同じ。承認の仕方は、チャットごとに権限モード（毎回確認・編集は自動で承認・Auto mode・計画）で選ぶ |

### 5.3 文書

| 優先度 | 機能 |
|---|---|
| Must | 要件定義書・スケジュールなどの文書は、リポジトリのファイル（`docs/requirements.md` など）として持ち、git で版管理する。AI はチャットの中でふつうにファイルを書く（Kickoff の DB には文書を持たない） |
| Must | 文書はファイルタブで見る・直す |
| Could | 資料フォルダ: ファイルをアップロードして置いておき、そのプロジェクトのチャットで AI が読み取り専用で読めるようにする（いまの「参照資料」は、Mac にある既存のフォルダ・ファイルを指す） |
| Should | チャットを開く場所を設定で選べる: ボードと分けた「チャット」タブ（初め。チャットを横幅いっぱいに出し、ボードのカードを押すとそのタブへ移る）/ ボードの右のパネル（ボードを見ながら開く）。どちらも同じタブなので、切り替えても開いているチャットはそのまま |
| Should | プロジェクトの「メモ」タブで、Markdown のメモをフォルダに分けて書ける（深い階層・名前の変更・ドラッグで移動・ゴミ箱。Obsidian と同じく ⌘S で保存し、Markdown 表示（ライブプレビュー）とそのまま表示を切り替えられ、どちらでも書ける。題名からその場で名前を変えられる）。保存先はプロジェクトの外（設定で親フォルダを選び、その下にプロジェクトごとのフォルダを自動で作る。プロジェクトごとに別の場所も選べる）で、Finder やほかのアプリでも開ける |
| Should | メモを AI で整理できる（見出しのボタンで本文の右にメモのチャット（メモごとに 1 つのふつうのチャット。メインのチャットと同じ入力欄・モデル選択・音声入力）を開き、相談しながらメモを作る。AI はメモを直接書き換え、本文はすぐ読み直す。本文で選んだ文は右クリックの「チャットに追加」で引用して入力欄に足す。メモのタブの「AI でフォルダを整理」で、名前の変更・フォルダ分けの案をチェックの一覧で見せ、選んだものだけを動かす） |
| Should | HTML のメモを作れる（「新しいメモ」で Markdown か HTML を選ぶ）。ページ（HTML と CSS を描いた見た目。中の JavaScript は動かさない）とソース（HTML をそのまま書く）を切り替え、メモのフォルダの CSS・画像も読める。メモのチャットに頼めば AI が HTML と CSS で書く |
| Should | チャットの画面の右の欄でメモを開き、会話を見ながら書ける（入力欄の上の「メモ」・「メモに追加」のあとの「開く」から。別ウィンドウで開くようにも設定で選べる） |
| Should | チャットの発言を右クリックして「メモに追加」（選んだ文、なければ発言の全体）。名前は「<チャット名> チャットメモ<n>」で自動に付け、あとで変えられる。AI で要約してから追加・既存のメモへの追記もできる。返答の文を選んだときの上のボタンにも「メモ ▾」（押すと、新しいメモ / 既存のメモ の入れ方を選ぶメニューを開く。右の欄の子チャット・サブエージェントの会話でも出す） |

### 5.4 エージェント実行（セッション）

| 優先度 | 機能 |
|---|---|
| Must | チャットでエージェントに指示する。追加の指示を出して会話を続けられる。チャットのモデル・推論の深さ・権限モードは入力欄で選ぶ |
| Must | チャットごとに作業場所（本体か git のワークツリー）を選ぶ。並行して進めるときは、チャットごとにワークツリー（ブランチ）を分ける |
| Must | 実行ログをリアルタイムで表示する（AI の発言・ツールの使用・コマンドの結果） |
| Must | 承認カード（許可 / 常に許可 / 拒否）と、AI の質問への回答 |
| Must | 中断と再開（アプリを再起動しても続きから再開できる） |
| Must | 複数チャットの並列実行（同時に動かす数は決めない。送った指示はすぐ動かす） |
| Should | 作業中に送る次の指示は、いまのやり取りに足す（いま）か送信待ちにためる（あとで）かを選べる。送信待ちは並べ替え・書き直し・まとめて送るができ、一時停止の印の位置まで送ったら止められる。送信ボタンの右クリックの「質問として送る」で、その指示の作業が終わったら一時停止し、答えを見てから次を決められる。送信待ちには「会話を圧縮」「コンテキストを消去」も挟め（見出しの「挟む」の「圧縮」「コンテキスト消去」・行の右クリックの「このあとで…」）、そこまで送ったら会話を圧縮する・これまでの会話を引き継がずに新しい会話にしてから次を送る（消去しても記録は残る）。見出しの操作は、挟む ｜ 送り方（自動で送る・すべて送る）｜ すべて消す のまとまりに分け、狭ければ 2 行にする。作業中の「会話を圧縮」の予約も送信待ちのいちばん上の行になる |
| Could | チャットごとにプロバイダー（Claude / Codex）を選ぶ |

### 5.7.1 ブラウザ

| 優先度 | 機能 |

### 5.7.2 ターミナル

### 5.13 AI の Kickoff 操作ツール

チャットの AI に Kickoff の操作（チャットの名前の変更など）をさせるときは、Kickoff の API を AI に開けず、AI 用の「Kickoff 操作ツール」に選んだ操作だけを入れる（作ったのは「子チャットを作る」（2026-11-12）と、【安全・そのまま実行】の操作すべて（2026-11-13）。決めた操作はすべて作った）。作り方は DB のツール（`kickoff_db`。`src/core/providers/claude/dbTools.ts`）・埋め込みブラウザの操作ツール（`src/core/providers/claude/browserTools.ts`）と同じ。操作は「安全（そのまま実行）」「承認カードで聞く」「ツールに入れない」の 3 つに分ける。API は画面でできることが全部できるので、AI が呼べると開発版と製品版のポートを取り違えて本物のデータを書き換える・自分を止める・`kickoff_db` の守り（読み取りだけ・承認・時間と行数）を SQL のタブ用の口から素通りする、が起きる。操作ツールなら、Web ページなどの指示に AI がだまされても、被害は選んだ操作の範囲で止まる。決めた形（ツールの名前・引数・範囲）は、下の【作った】の行に書く。新しい操作を足すときも、同じ 3 つの分けで決める。ツールはどれも MCP のサーバー `kickoff_chat`（`src/core/providers/claude/chatTools.ts` がまとめ、まとまりごとに `chat*Tools.ts`）で、中身はプロバイダーに依らない `src/core/chat/ai*.ts`。

### 5.14 Docker

Docker Desktop・OrbStack を開かずに、プロジェクト（本体とワークツリー）の compose のサービスだけを見て、起動・停止し、ログを見てシェルを開く（段階 1 は作った（2026-11-13。タブ・一覧・操作・ログの画面・シェル・ポートの取り合い・AI の守り）。段階 2「DB で開く」も同じ日に作った）。方針は「なるべく軽く、でも便利さは落とさない」。`docker` コマンドを通すので、Docker Desktop・OrbStack・Colima のどれでも、いま選ばれている docker context にそのままつながる。Docker の本体（エンジン）は管理しない。詳しい仕様はメモの「Docker 仕様書」（段階 1・段階 2 は決定・2026-11-13。確かめた環境は Docker 29.8.2・Compose v5.5.0・OrbStack）。作る順は 段階 1（タブ・一覧・操作・ログの画面・シェル・ポートの取り合い・AI の守り）→ 段階 2（DB で開く）。

しないこと: コンテナ（片付けで消す使い捨ては別）・イメージ・ボリューム・ネットワークの削除と `down -v`、build・pull を単独で流す、compose を使わずにコンテナを作る、Docker の本体の起動・停止・設定、すべてのコンテナ・イメージ・ボリュームの一覧、CPU・メモリの使用量、ログの保存（ログの画面を閉じたら捨てる）、開発サーバー（コンテナでないもの）の起動・停止（静かなぶつかりの相手が Homebrew のサービスのときだけは別）、Kubernetes・リモートの Docker、ワークツリーでポートを自動でずらす、スマホからの Docker タブの操作。本体とワークツリーで組の名前・ポートを確実に分ける仕組み（並行レビューのため）は、別の機能「ワークツリーの実行環境」（メモの「ワークツリーの実行環境 仕様書」。下書き）で詰める。

### 5.16 ワークツリーの実行環境

ワークツリーごとにポートの番号と Docker の組の名前を分け、本体と複数のワークツリーのアプリを同時に動かして、ブラウザで並べてレビューできるようにする（段階 1・段階 2 を作った・2026-11-13）。詳しい仕様はメモの「ワークツリーの実行環境 仕様書」。ワークツリーを作るときに決め、起動のたびには調べない。書くのは Git で管理していないファイルだけ。

### 5.17 ポートを使っているプロセス

| Should | 出すもの: ポート（いくつも待っていれば 1 行）・短いコマンド（乗せると全文）・プロジェクト・作業場所の札・動いている時間・起動元（Kickoff の中 / 切り離されている / ほかのアプリ。親をたどって決める。切り離されているものは残ったものの見分けになる）。ワークツリーの帯の中の番号なら、いつも「feat-x の帯（開発サーバー）」と添え、帯の持ち主とプロセスの作業場所が違えば ⚠。Kickoff 自身とその祖先・プロジェクトの外のプロセスは出さない |

## 6. 非機能要件

- **ローカル完結**: データは Mac 内（SQLite）に置く。外部に送るのは AI プロバイダーへの通信と、任意で有効にする通知だけ
- **セキュリティ**: 外部からのアクセスはトークン必須。デプロイやリポジトリ外への書き込みなど、影響の大きい操作は承認制
- **使用量**: サブスクリプションの上限を意識する（API 換算の推定コストを表示）
- **拡張性**: プロバイダーを追加しやすくする。HTTP API はデスクトップの画面・スマホのブラウザ・将来のネイティブアプリで共通にする
- **復旧性**: アプリが落ちても、中断した実行を続きから再開できる
