# コア（src/core）の説明

Electron に依存しないサーバー（HTTP API・SQLite・エージェントの実行）。メインプロセスの中でも、`npm run daemon`（`daemon.ts`。保存先とポートは開発版のもの）の単体でも動く。画面と共有する型と純粋な関数は `src/shared`（`@shared/…`）に置き、画面（renderer）のコードは import しない。チャットの実行は `chat/CLAUDE.md`、プロバイダーは `providers/CLAUDE.md`。

## フォルダの役割

- `index.ts`: `startCore` で組み立てて起動し、`close` で止める（実行中のエージェント → 流れ続けている外部コマンド → 音声のダウンロード → 使用枠 → 自動のアーカイブ → メモの見張り → HTTP → DB）。起動のときに、リリース前の保存データを消し（`discardPrereleaseData`）、前回の終了で作業中のまま残ったチャットを未読の失敗にする（`store.chats.recoverInterrupted`。そのチャットの ID は、起動したときの送信待ちの確かめで「続けてから送る」を選べるよう `Runner` に渡す）。
- `bus.ts`: 変更の知らせ `Bus`（`@shared/types` の `BusEvent`。SSE で配る）。
- `db/`: SQLite（`node:sqlite`）。→「DB」
- `http/`: Hono の API・認証・SSE・画面の配信。→「HTTP」
- `chat/`: チャットの実行（受付の `Runner`・1 回の実行・送信待ち・止まったあとの再開・承認・分岐と巻き戻し・書き込みの守り・添付）。→ `chat/CLAUDE.md`
- `providers/`: エージェントの実行基盤の抽象（`AgentProvider`）と Claude Code の実装。→ `providers/CLAUDE.md`
- `git/`: Git・GitHub（gh）・プロジェクトのフォルダの作成と取り込み・ワークツリー。→「Git」
- `github/`: GitHub タブの読み取り（issue・PR の一覧と中身）と書き込み（`writes.ts`）、CI のタブ（`ci.ts`）。→「Git」の「GitHub タブ」「CI のタブ」
- `usage/`: Claude のプランの使用枠と、ほかのサービスの使用状況。→「使用状況」
- `voice/`: 音声入力の文字起こしと、音声モードの読み上げ（OpenAI の声）。→「音声入力」
- `memos/`: プロジェクトのメモ（`memos.ts` の `MemoService`）。→「メモ」
- `databases/`: DB クライアント（`service.ts` の `DatabaseService` と、DB に触る別のプロセス DB ワーカー）。→「DB クライアント」
- `docker/`: Docker タブ（プロジェクトの compose の一覧・操作・docker events）。→「Docker タブ」
- `browser/`: AI に埋め込みブラウザを操作させる口 `BrowserControl`（`control.ts`。タブのある欄を開いて表に出す `reveal` と、開くときの表に出す頼み `RevealRequest` も。コアは Electron に依らないので、中身はメインプロセスが `startCore({ browser })` で渡す（`main/browser/agentBrowser.ts`）。単体のコア（`npm run daemon`）では渡されず、AI にブラウザのツールを出さない）と、AI に返す文の組み立て（`format.ts`: タブの一覧 `formatTabs`（このプロジェクトのタブを先に）・ページの読み取り `formatSnapshot`（押せる要素の番号 ref と見えている文。文は `SNAPSHOT_TEXT_MAX` で切る）・URL の補い `normalizeBrowserUrl`（localhost・ポート付きは http、ほかは https。http(s) 以外は開かない））。ツールそのものは `providers/claude/browserTools.ts`。
- `system/`: 外部コマンド・パス（→「外部コマンドとパス」）・ログインシェルの PATH（`shellEnv.ts` の `loadLoginShellPath`）・期限付きのキャッシュ（`ttlCache.ts`）・名前と保存先とポート（`appEnv.ts` の `APP_ENVS`。製品版 Kickoff = 4317、開発版 Kickoff Dev = 4318。同時に動かせ、開発中の変更で製品版のデータを壊さない）・開発版のデータの写し（`devData.ts` の `seedDevData`。開発の保存先がなければ製品版から一度だけ。DB は `VACUUM INTO`）。
- `testing/`: テストからだけ使う補助。→「テスト」

## DB（db/）

- スキーマは `db/schema.ts` の `MIGRATIONS` に追記して変える（既存の要素は書き換えない。v1 は `SCHEMA_V1`）。版ごとに 1 つのトランザクションで流す。
- 表はすべて STRICT。真偽値は `CHECK (x IN (0, 1))`、JSON の列は `CHECK (json_valid(x) AND json_type(x) = 'object')`（配列なら `'array'`）。値の一覧（状態・権限モードなど）は CHECK にしない（増やすたびに表を作り直すことになるため）。「ない」は NULL で、空文字を入れない列は `CHECK (x <> '')`（`worktree_path` が NULL なら本体）。
- 版は `PRAGMA application_id`（`APPLICATION_ID` = 'KICK'）と `user_version`（`USER_VERSION_BASE` の 200 ＋ 版。v1 = 201）で持つ。触る前に `inspectSchema` で調べ、Kickoff のものでない・このアプリより新しい版なら、データに触らずに例外にする。
- リリース前の系統（印が KICK で `user_version` が 100 ＋ 版）は引き継がない。起動のときに `db/open.ts` の `discardPrereleaseData` が DB（`-wal`・`-shm` も）・`backups/`・`uploads/` を消し、空の DB から作る（音声のモデル・トークンなど DB に依らないものは残す）。`openDatabase` はリリース前の DB を開かない。古い DB を変換する仕組みは作らない。
- `openDatabase` は WAL と外部キーを有効にしてから `migrate` する。
- `Store`（`db/store.ts`）は表ごとの店をまとめて持つだけ: `store.settings` / `secrets` / `projects` / `groups` / `chats` / `events` / `queues` / `snippets`（定型文）/ `prNotices`（ワークツリーの PR の確認を閉じた覚え。v11 の `pr_notice_dismissals`）/ `dbConnections`（DB クライアントの接続。v13 の `db_connections`）/ `dbQueryHistory`（SQL の履歴。v14 の `db_query_history`）/ `dbErLayouts`（ER 図で動かした位置。v15 の `db_er_layouts`。知らせは出さない）。接続の手順メモ `memo_path` は v16、SSH トンネル `ssh` は v17、準備のコマンド `prep` と記録 `dbPrepRuns`（v18 の `db_prep_runs`）は v18。チャットと GitHub の issue・PR の結び付き（`chats.github_repo` / `github_number` / `github_kind`。3 つがそろって入るか、そろって NULL かは店で守る。付け外しは `store.chats.setGitHub`（最後に動いた時刻は進めない））は v19。CI の失敗を知らせるか（`projects.ci_watch`）と知らせた実行（`ciNotices`。表 `ci_failure_notices`）は v21。各店は `db/<表>.ts` の `createXxxStore(db, onChange)` で、変える操作は `onChange` で知らせる（SSE の起点。秘密の値は知らせず、送信待ちの知らせは `ChatRuntime` が出す）。ルートなどから SQL を書かず、店を直接使う。作るときの入力の形は `db/types.ts`（`NewProject` / `NewChat`）。
- 行と型の変換は各店の `toChat` / `toProject` などに集める（真偽値は `db/common.ts` の `bit()` で 0 / 1、JSON の列は読み書きのときに変換）。型と API は boolean で返す。変えられる列の一覧（`CHAT_COLUMNS` / `PROJECT_COLUMNS`）を型と UPDATE の両方に使い、`updateRow` で書いた項目だけを変える。
- チャットのアーカイブは `store.chats.archive`（子孫も一緒。決まりは `chat/CLAUDE.md` の「子チャット」）。
- `chats.active_at`（最後に動いた時刻。一覧の並び順）を進めるのは、状態（`status`）を変える更新だけ（`chats.update` に `status` があるとき = 送った・終わった）。未読・固定・グループ（`setUnread` / `setPinned` / `setGroup`）・手動の並び（`reorder`）・名前・アーカイブ・移動・作業場所の片付け・起動のときの復旧では進めない。
- チャットの手動の並び（`chats.position`。v10。画面のサイドバーの並び順「手動」）は、プロジェクトの中の 1 本の並び（小さいほど上。NULL = まだ並べていない新しいチャット）。`store.chats.reorder(projectId, ids)` が ids の何番目かを振り（ほかのプロジェクトのチャット・ids にないチャットは変えない）、変わったチャットだけ知らせる（`PUT /api/projects/:id/chats/order`）。
- チャットを入れられるのは同じプロジェクトのグループだけ（トリガーで守る）。色（`hue`）はプロジェクトもグループも、作ったときに `@shared/project/colors` の `pickProjectHue` でほかと被らない色を選ぶ（グループは同じプロジェクトの中で）。
- 全文検索: `chat_events` の生成列 `text`（自分の発言とメインの AI の返答。サブエージェントの文は除く）を、ビュー `chat_event_texts` を中身にした FTS5（trigram）の `chat_event_search` にし、トリガーで追従させる。`store.events.search` は 3 文字以上を MATCH、2 文字以下を生成列の LIKE で探す。フィード（`GET /api/feed`。全プロジェクトの画面）は `store.events.feed`: 子チャット・メモのチャットを除くチャットごとに、メインエージェントの最新の返答（`type = text` で `parent` のないもの）1 件の初めの `FEED_TEXT_LIMIT`（400）文字を、返答の新しい順に返す（チャットごとに索引 `(chat_id, id)` を新しい方からたどる相関副問い合わせ）。
- 設定はキーごとの JSON（`store.settings.get` が `DEFAULT_SETTINGS` とマージし、知らないキーは返さない。`update` は送った項目だけで、`chat_defaults` は丸ごと置き換える）。
- 秘密の値（API キーなど）は `secrets` の表（`store.secrets.get` / `set`。名前は `SecretKey`）。設定・SSE・API の応答には出さず、保存したかだけを返す。
- `meta` の `database_id` は DB を作ったときに決める ID。`/api/status` で返し、画面は DB を作り直したら ID 入りの表示の状態を捨てる目印にする。
- 性能の記録に載せる DB の様子は `db/stats.ts`（`Store.stats()` → `Core.databaseStats()`。メインプロセスは SQL を流さない）。

## HTTP（http/）

- ルートは `http/routes/<領域>.ts` に `xxxRoutes(app, deps)`（`deps` は `ServerDeps`）として書き、`http/server.ts` の `createApp` で登録する。登録は認証のミドルウェア（`/api/*`）と `onError` より後、SSE・知らない API の JSON の 404・画面の配信より前で、いまの順を崩さない。チャットの資源（一覧・作成・詳細・変更・既読・手動の並び・別のプロジェクトへの移動・削除・検索・フィード・GitHub の issue・PR との結び付き `PUT|DELETE /api/chats/:id/github`。新しいチャットの本文の `github` でも付く）は `chats.ts`、実行（送る・伝える・圧縮が終わるまで預かった指示を外す・止める・圧縮・自動の再開をやめる・裏の作業を止める・分岐・巻き戻し）は `turns.ts`、送信待ち（起動したときの送信待ちの確かめ `GET|POST /api/queue-resumes` も）は `queue.ts`、回答待ちは `approvals.ts`、添付とほかのチャットの記録・ツールの結果の画像は `uploads.ts`、Git は `git.ts`（状態・差分・差分の元の中身・操作・履歴・ブランチ・タグの操作と途中のマージ・リベース・PR）/ `files.ts`（ファイルの一覧・中身・検索・置換・保存・作る・名前の変更・ゴミ箱）/ `worktrees.ts` / ワークツリーの PR の知らせ `worktreePrs.ts`、メモは `memos.ts`、定型文は `snippets.ts`（一覧・作る・並べ替え・変更・削除）。
- URL の `:id` は `http/lookups.ts` の `lookups(store)` が返すミドルウェアで引き当て、ハンドラーは `c.var` で受ける（`withProject` / `withChat` / `withGroup` / `withSnippet`。Git・ファイル・検索・/ のコマンドは、操作するフォルダも `c.var.workdir` に入れる `withWorkdir`）。番号でなければ 400（`idParam`）、なければ 404。ルートごとに引き当てと検証を書かない。ID で引くのは `requireProject`、ほかのプロジェクトのグループを断るのは `requireGroupOf`（400）。
- 作業場所の指定（`?worktree=`・新しいチャットの `worktree_path`）は `http/workdir.ts` の `requireWorktree(repo, worktree)` で解決する（null = 本体 / このプロジェクトのワークツリーでなければ 400 / フォルダが消えていれば 404）。チャットの作業場所のフォルダは `chat/workdir.ts` の `workdirOf`。
- 失敗は例外で伝える。ドメインのコード（`chat/`・`git/`・`voice/` なども）は `http/errors.ts` の `Invalid`（400）/ `NotFound`（404）/ `Conflict`（409）を投げ、`onError` が `errorResponse` で `{ error }` にする。zod の失敗は 400（`issues` 付き）、外部コマンドの `CommandError` はその文のまま 400、知らない失敗は 500（記録する）。外の SDK の失敗は `.catch(asInvalid)` で 400 にする。ルートで boolean を受けて 404 にしたり、例外を包み直したりしない。作業中にできない操作は `runner.requireIdle(chatId, "削除")` のように 409 にする。
- 入力: JSON の本文は `http/input.ts` の `jsonBody`（空なら {}、JSON でなければ 400）だけで読み、クエリは `queryOf`。形は zod の `parse` で確かめ（失敗の 400 は `onError` に任せる）、共通の形と上限は `routes/schemas.ts`（`optionalId` / `repoPath` / `folderPath` / `flag` / `branchName` / `groupName` / `projectName` / `queueId` / `chatOptionsSchema` / `attachmentsSchema`（種類 `kind` で分けた形。kind のない古い形も受け取り `normalizeAttachment` で読み替える）/ `messageText` など）。送る指示（文・選択・添付。文が空でも添付があれば送れる）は、新しいチャット・続き・止めずに伝える・送信待ちで同じ形にする（`newChatSchema` / `messageInputSchema` / `queueMessageSchema`）。本文の型は `@shared/types` の `api.ts`（`…Body`）に置き、zod は `satisfies z.ZodType<…>` で合わせる。
- 応答: 変えたら、変えたあとの資源（チャット・プロジェクト・グループ。並べ替えは一覧）を返す。作ったら 201、待たずに始めたら 202。削除と、様子が変わるだけで返すものがない操作（止める・自動の再開をやめる・回答する）は 204（変わった様子は SSE で届く）。送信待ちを変える API はどれも、変えたあとの `QueueState`。Git の操作は `gitAction` で操作のあとの状態を返す。API にだけ出る応答の形も `api.ts`。
- 認証はトークン（保存先の `token`。`loadOrCreateToken`）を Cookie（`kickoff_token`）か `Authorization: Bearer` で受ける。スマホは `/pair?token=` で Cookie に移す。
- SSE（`GET /api/events`）は `Bus` の知らせを JSON で送る。つないだらすぐ最初の行（ping）を送る（書くまで応答ヘッダーが届かず、画面が「接続中」のままになる）。切断の知らせ（`onAbort`）は最初の `await` より前に登録する。知らせの出どころ: DB の変更は各店の `onChange`、作業中の様子は `ChatRuntimes` の `chat_live`（変わるたびに丸ごと）、返答の途中経過 `chat_delta`・サブエージェントの途中経過 `chat_subagent`・実行中のコマンドの出力 `chat_command_output`（保存しない）、回答待ちは `ApprovalCenter`、使用枠は `UsageMonitor`、音声のモデルのダウンロードは `VoiceService`。種類を足すときは `BusEvent` に足す。
- 製品版の画面の配信（`Cache-Control: no-cache`・拡張子のあるパスは 404）と、HTTP サーバーの止め方（`stopHttpServer`）の決まりは `src/main/CLAUDE.md`。

## 外部コマンドとパス（system/）

- 流れ続けるコマンド（`docker events`・中止できる `docker compose up -d`）だけは `system/stream.ts` の `streamCommand`（spawn。標準出力・標準エラーを 1 行ずつ渡し、`stop()` で SIGTERM → 3 秒で SIGKILL、`done` は終了コードと標準エラーの最後の行を返して reject しない）で動かす。すぐ終わるものは `runCommand` のまま（どちらにするかはコマンドごとに決めておく）。動いているものはコアを閉じるときに `stopAllStreams` で聞かずに止める。
- コアの外部コマンドは `system/exec.ts` の `runCommand(file, args, opts)` で動かす（標準出力を返す。失敗は `CommandError` で、文は標準エラー、なければ元の例外の文。`okCodes` の終了コードは失敗にしない。標準出力の上限は既定 20MB）。コアで `execFileAsync` を直接使わない。`CommandError` はそのまま投げれば 400 になる。
- 認証などを聞かれても答えられないので、git・gh は `nonInteractiveEnv()` で待たずに失敗させる。git は `git/exec.ts` の `gitOutput` だけを通す。
- 実行ファイルは `findExecutable(names, searchDirs())` で探す（PATH の順 → `/opt/homebrew/bin` → `/usr/local/bin` → `~/.local/bin`。Finder から起動してログインシェルの PATH を取り込めなかったときの補い）。
- パスの包含判定・`~` の展開・リンクの解決は `system/paths.ts`（`isInside` / `expandHome` / `realPathLoose` / `realPathOrSelf`）、期限付きのキャッシュは `ttlCache`（モデル・/ のコマンドの一覧）。例外の文は `@shared/errors` の `errorMessage`。

## DB クライアント（databases/）

プロジェクトごとに登録した DB（SQLite・PostgreSQL・MySQL / MariaDB）を見る・SQL を流す（要件 5.12。画面は `features/database/CLAUDE.md`）。

- 接続は表 `db_connections`（v13。店は `db/dbConnections.ts`。並びは `position`）。パスワードは `secrets` の `db_connection:<ID>:password`、AI 用のユーザー（`ai_username`。v14）のパスワードは `:ai_password`、SSH のパスワードは `:ssh_password` に置き、応答には `has_password` / `has_ai_password` / `has_ssh_password` だけを返す。値はいつも `safeStorage`（キーチェーンの鍵）で暗号化して置く（2026-11-11 に決めた。要件 5.12。AI がパスワードを知ると `psql` などで直接 DB に入れ、AI のツールの守りが素通りになるため。暗号化と復号はメインプロセスが `startCore` に渡す口で、コアは Electron に依らない。口のない単体のコア・テストだけ暗号化せずに置く予備。暗号化を入れた版の最初の起動で、暗号化せずに置いていた DB のパスワードを一度だけまとめて暗号化して置き換え、暗号化していない値は消す。署名は仮の署名（ad-hoc）のままなので、製品版を入れ替えたあと最初に使うときに 1 回キーチェーンの許可を聞かれる）。キーチェーンで拒否されて開けないときは、DB タブから接続したならその場でパスワードを聞き、入れた値は Kickoff を終えるまでコアのメモリにだけ持って、その接続のほかのタブ・AI のツールでも使う（保存した値は消さない）。AI のツールからなら失敗にして「利用者に DB タブから接続し直してもらってください」と返す。仕組みは `databases/secrets.ts` の `DbSecretVault`（`startCore` の `secretCipher` を受ける。`DatabaseService.vault`）: ルートが保存する前に `seal` で暗号化し（作る・取り込む・変える。写すときは暗号化したまま写す）、`safe:v1:<base64>` の形で置く（印のない値は暗号化していないもの）。つなぐ先を組み立てる `DatabaseService.target`（非同期）が `read` で開き、開いた値は起動している間覚え（同時に読んでもキーチェーンには 1 回）、開けなければ覚えずに `DbPasswordLocked`（409・`code: "db_password_locked"` = `DB_PASSWORD_LOCKED`）。その場で入れた値は `enter`（`POST …/:cid/entered-passwords`。本文 `DbEnteredPasswordsBody`。入れた種類だけ。204）、パスワードを保存し直す・接続を消すと `forget`。AI のツール（`aiTools.ts` の `askUserIfLocked`）は `DbPasswordLocked` を「…利用者に DB タブから接続し直してもらってください」の失敗にする。置き換え（`migrate`。`startCore` が待たずに流す）は `store.secrets.replaceSecurely` で書き、`secure_delete` と WAL の切り詰めで元の値をファイルに残さない（暗号化している間に変わった値は置き換えず、次の起動で）。接続を消すと、表のトリガー `db_connections_drop_secrets` がそのパスワードも消す（プロジェクトを消したときの連鎖の削除でも効く）。変えたら SSE の `db_connections`（プロジェクトの ID だけ。中身は載せない）。
- API は `http/routes/databases.ts`（`/api/projects/:id/db-connections`。接続の一覧・作る・変える・並べ替え・写す（ほかのプロジェクトからは名前のまま・手順メモなし、同じプロジェクトの中なら名前に「 のコピー」を付けて手順メモも同じもの）・試す（結果に、つなぐのにかかった時間 `duration_ms`）・消すと、DB・スキーマ・テーブルなどの一覧・テーブルの詳細・関数と列挙型の定義（`/definition`）・行・数・補完の名前・ER 図の中身と動かした位置・SQL・SQL の履歴・SQL のタブの接続の止める / コミット / 取り消す / 閉じる・テーブルの行の変更の保存（`/edits`））。すべて 127.0.0.1 から来たものだけ受け、ほかは 403（`localOnly`。リモートのアクセス・スマホからは使わせない）。`?worktree=` で SQLite のファイルを開く作業場所を選ぶ。
- SQLite のファイルはプロジェクトフォルダからの場所（`/` か `~` からなら外のファイル）で、ワークツリーでは中の同じ場所を開く。ないときは 404 と `code: "db_file_not_in_worktree"`（`DB_NOT_IN_WORKTREE`。画面が「本体のものを開く」を出す）。Kickoff のデータのフォルダの中のファイルは、実体のパスで比べて断る（自分の DB を書き換えさせない）。
- DB ワーカー（`databases/worker/`）: DB に触るのは別のプロセス（`client.ts` の `DbWorkerClient` が立ち上げる。Electron ではメインプロセスが `utilityProcess` で `out/main/dbWorker.js` を起動する口を `startCore` に渡し（製品版は Electron の fuses で RunAsNode をオフにするので、`ELECTRON_RUN_AS_NODE` で `process.execPath` を Node として動かす形は使わない。2026-11-11 に決めた）、開発の単体のコア・テストでは `worker/main.ts` を tsx で `child_process.fork`（`entry.ts`））。重い SQL・止まった DB がコアの HTTP と SSE を止めないため。メインプロセス（コア）はドライバ（pg・pg-cursor・mysql2）を読み込まない（起動を遅くしないため。仕様の「起動を遅くしない」）: テストで同じプロセスで動かすつなぎは `inProcessWorker.ts` に分けて `client.ts` から import しない、取り込みの `yaml` は探すときに `import()`、ワーカーの中でも pg・mysql2 は使う接続を開くときに `import()`（`handler.ts` の `openDriver`）。`out/main/index.js` が `pg` / `mysql2` / `yaml` を直接 import していないことをビルド結果で確かめる。頼みは `{ id, method, params }` → `{ id, ok, result | error }`、止めるのは `{ cancel: id }`（`protocol.ts`）。5 分使わなければ止め（トランザクションの途中の接続があれば止めない）、落ちたら待っている頼みを失敗にして、次の頼みで立ち上げ直す。SQLite（`node:sqlite`）は同期で途中で止められないので、止めるときはワーカーごと止める。ワーカーが起動する ssh・シェルは `worker/children.ts` の `spawnTracked` で自分のプロセスグループにして pid をコアへ知らせ（`ChildProcessEvent`）、ワーカーを止めた・落ちたときに `DbWorkerClient` がそのグループごと止める（`utilityProcess` のワーカーは自分のプロセスグループを持てないため）。
- 接続（ワーカーの中のセッション）: 木・テーブルのタブは接続・作業場所・DB ごとに共有（`shared:<接続>:<作業場所>:<DB>`。PostgreSQL は DB ごとにつなぐ）、SQL のタブはタブごと（`sql:<接続>:<タブのキー>`）。つなぎ先が変わったら開き直す（トランザクションの途中なら断る）。`DB_SESSION_IDLE_MS`（10 分）使わなかった接続はワーカーが閉じる（`handler.ts` の `closeIdle`。ワーカーの中で 1 分ごとに見る。トランザクションの途中・流している最中のものは残し、使ったトンネルも返す。その接続の接続（名前の 2 段目 `connectionIdOfSession`）がすべて閉じたら、準備の後片付けも流す（仕様の「何もしない状態で自動で切れたときも」。IP の許可などを開けっぱなしにしない。準備を流している最中は流さない）。トランザクションの途中の SQL のタブは画面がコミットか取り消しを聞いてから閉じる）。手で切るのは `POST …/:cid/disconnect`（`DatabaseService.disconnect`: その接続の木・SQL のタブ・AI の接続をすべて閉じてトンネルを止め、後片付けを流す。コミットしていない SQL のタブがあれば、`force` でなければ切らずにそのタブを `pending_sessions` で返す。`force` なら取り消して切る）。つないでいるか: ワーカーは接続を開いた・閉じたときに知らせ（`SessionEvent`。`handler.ts` の `sessionOf` / `dropSession`）、`DbWorkerClient` が開いている名前を覚えて、ワーカーが止まった・落ちたら開いていたものすべてを閉じたことにする。`DatabaseService` は木・テーブル・SQL のタブの接続（`shared:` / `sql:`。AI・行の保存の接続は 1 回ずつなので数えない）を接続ごとに数え、0 ↔ 1 以上が変わったら SSE の `db_connection_state`（`connection_id`・`connected`）を出す。いまつないでいる接続は `GET …/db-connections/connected`（`{ ids }`）。同じ名前の接続への頼み（コミット・取り消しも）は `handler.ts` の `serial` で 1 つずつ流す（木の段・テーブルのタブは同時に頼むので、並べるとまだない接続をそれぞれ開いて 1 本が閉じられずに残り、1 本の接続に文を重ねて送ることになる）。閉じるのは待たない。
- ドライバ（`worker/driver.ts` の `DbDriver`）: SQLite は `worker/sqlite.ts`（`node:sqlite`）、PostgreSQL は `worker/postgres.ts`（pg。1 つの接続は DB 1 つ。SQL はカーソル（pg-cursor）で上限 ＋ 1 行だけ読む。表の作る文は返されないので列・制約・インデックス・トリガーから組み立てる。止めるのは別の接続から `pg_cancel_backend`。トランザクションの様子は ReadyForQuery の印）、MySQL / MariaDB は `worker/mysql.ts`（mysql2。DB は名前で指す。結果の列の型の名前は `mysqlTypeName`（TEXT の列も BLOB の型の番号で届くので、文字コードがバイナリでなければ text）。SQL の行は流れてくるまま受け、上限を超えたら別の接続から `KILL QUERY` で止めてそこまでを返す。止めるのも `KILL QUERY`。トランザクションの様子は OK の応答のサーバーの印）。木の段（`objects`）はテーブル・ビューのあとに関数・列挙型を並べ（テーブルにはおおよその行数 `estimated_rows`: PostgreSQL は `reltuples`（統計の前の -1 は null）、MySQL は `TABLE_ROWS`、SQLite は ANALYZE の `sqlite_stat1`（なければ null）。ビューは null）、定義（`definition`）を返す: PostgreSQL は `worker/postgresRoutines.ts`（関数とプロシージャ。拡張が入れたものは除く。同じ名前の別の引数があるので名前は `名前(引数)` で、定義もその形で引く。作る文は `pg_get_functiondef`、列挙型は `pg_enum` の値から組み立てる）、MySQL / MariaDB は `worker/mysqlRoutines.ts`（`information_schema.ROUTINES`。関数とプロシージャは名前で 1 つにし、同じ名前なら関数。作る文は SHOW CREATE、権限がなければ本文だけ。列挙型は列の型なので段に出さず、定義は 400）、SQLite は関数・列挙型がないので 400。日時の型は文字列のまま受け取る（Date にするとこの Mac の時間帯でずれて見える）。つなぎ方の共通（TLS・待つ時間・名乗る名前 Kickoff）は `worker/network.ts`。DB が接続を切ったら（`alive()` が false）、次の頼みでつなぎ直す（pg は切れたときカーソルが答えを返さないことがあるので、流している文は driver が失敗にし、ReadyForQuery を待たない）。
- 書き込む前の確かめ（接続の `write_check`。v20。既定は `DB_ENVIRONMENT_DEFAULTS` の環境から。作るときに省けば環境の既定）は画面だけで確かめる（`features/database/CLAUDE.md`）。コアは値を持つだけで、流すときには見ない（読み取り専用の守りとは別）。
- 読み取り専用の接続は 2 段で守る: 文の判定（`@shared/database/sqlStatements.ts` の `isReadOnlyStatement`）と DB 側の読み取り専用（SQLite は `readOnly` で開き、`setAuthorizer` で ATTACH / DETACH も断る（ほかの SQLite のファイルを開いて読ませない）、PostgreSQL は `SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY`、MySQL は `SET SESSION TRANSACTION READ ONLY`）。SQL のタブの「書き込む」の間（本文の `write: true`）だけ両方を外す（DB 側はつなぎ先の `read_only` が変わるので、そのタブの接続を開き直す。トランザクションの途中なら断る）。SQL は 1 回に 1 文だけ受ける（`node:sqlite` の `prepare` は 2 つ目からの文を黙って捨てるため。画面が文に分けて 1 つずつ送る）。結果は `DB_SQL_MAX_ROWS`（1000 行）まで（「さらに読む」は本文の `offset`: 読み取りの文だけ同じ文を流し直し、ドライバの `query` の `skip` で頭を飛ばして続きを返す。履歴には残さない。PostgreSQL はカーソルで 1000 行ずつ読み捨て、MySQL は受けて捨て、SQLite は `iterate` で飛ばす）、テーブルの行は `DB_TABLE_PAGE_ROWS`（100 行）ずつ。値は `worker/values.ts` の `toDbValue`（バイナリは大きさと頭だけ。全体の行を読むとき（`full`）だけ、`DB_IMAGE_PREVIEW_BYTES`（5MB）までの画像（`dbImageType`）に `data_url` を付ける。`DB_VALUE_HEAD_CHARS`（1 万文字 ≒ 10KB）を超える文字は頭だけの `DbLongText`（`{ long, head, chars }`）。テーブルの行の詳細などで残りが要るときは `POST …/:cid/full-row`（本文 `DbFullRowBody`: 場所・テーブル・行を指すキーの列の条件。`DatabaseService.fullRow` がワーカーの `rows` を `full: true` で 2 行まで読み、ちょうど 1 行でなければ 404 / 400）。AI の CSV の書き出しは全体のまま）。
- SQL のタブの「AI に頼む」（`POST …/:cid/sql-assist`。本文 `DbSqlAssistBody`: 場所・頼み・いまの SQL → `{ sql }`）: 「AI に見せない」接続は 400。場所のテーブルと列の名前（`outline`。値は渡さない）といまの SQL と頼みを `databases/sqlAssist.ts` の `sqlAssistPrompt` にして、プロジェクトのプロバイダーの `ask`（sonnet）に 1 回だけ聞き、答えの最初のコードの囲みを `parseSqlAnswer` で取り出す（空なら 400）。テーブルと列の名前は `SQL_ASSIST_SCHEMA_CHARS`（3 万文字）まで。
- テーブルの行の変更の保存（要件 5.12 の段階 3。`POST …/:cid/edits`・`DatabaseService.applyEdits`）: 本文は形のある変更 `DbRowEdit`（`update` / `insert` / `delete`。1 回に `DB_EDITS_MAX` 件まで。値は文字か NULL で、型は DB が読み替える）で、SQL は画面でなく `@shared/database/dbEdit.ts` の `editStatements` が組み立てる（場所つきの名前・値はいつも params・NULL のキーは `IS NULL`・真偽のキーは PostgreSQL なら 'true' / 'false'、ほかは 1 / 0・変える列のない更新は飛ばす・列のない追加は既定値で）。ワーカーの `apply`（`handler.ts` の `applyStatements`）が、保存ごとの新しい接続（`edit:<接続>:<uuid>`。終わったら閉じる）で BEGIN → 文を順に → COMMIT し、更新・削除がちょうど 1 行に当たらない（`expect`）か DB が断れば ROLLBACK して「n 番目の変更…すべて取り消しました」を返す（MySQL は mysql2 の FOUND_ROWS で、同じ値への更新も 1 行と数える）。読み取り専用の接続は `write: true`（テーブルのタブの「書き込む」の間）でなければ断る（400）。保存は見せる文（`preview`）を `;` でつないで SQL の履歴に 1 件で残す（行の数は合計、失敗なら失敗の文）。スキーマは変えない。
- チャットの AI の読み取り（要件 5.12 の段階 2。SDK のプロセス内の MCP サーバー `kickoff_db`。`providers/CLAUDE.md`）: 中身はプロバイダーに依らない `aiTools.ts` の `createDbAiTools`（`DbAiTools`: `connections` / `objects` / `describe` / `query`）。`turn.ts` の `buildTurnParams` が、プロジェクトに AI に見せる接続（`ai_access` が `none` でない）があるときだけ `ProviderTurnParams.database` に入れる（`hasAiConnections`。`Runner` の `databases`）。接続は呼ぶたびに店から引き直し（作業の途中で許可を変えたら次の呼び出しから効く）、名前で引く（1 つだけなら省ける。見せない接続は名前を出さずに断る）。SQLite のファイルはチャットの作業場所（`worktree_path`）で開く。一覧・構造は木と同じ共有の接続で読み、SQL は `DatabaseService.aiQuery`: 読み取りの 1 文だけ（`assertAiSql`。承認を聞く前にも確かめ、流せない文は聞かない）→ 承認して見せる接続は利用者に聞く（`query` の `approve`。断られたら理由の文で失敗）→ DB 側は接続の設定によらず読み取り専用（`read_only: true`）・AI 用のユーザーがあればそれでつなぐ → 呼び出しごとの新しい接続（`ai:<接続>:<UUID>`。SET などの状態を残さず、終わったら閉じる）→ `DB_AI_TIMEOUT_MS`（30 秒）で止める（手元で止めるのに加えて、DB の側にも 5 秒長い上限を付ける（`DbTarget.timeout_ms`。PostgreSQL は `statement_timeout`、MySQL は `max_execution_time`（SELECT だけ）、MariaDB は断られたら `max_statement_time`。ワーカーが落ちても DB の中で流れ続けないため。手元の方が先に止めて時間切れの文を返す）。30 秒を超えそうな SQL は、AI が `db_query` の `timeout_minutes`（分。上限なし）を付けて頼み、自由に見せる接続でも必ず承認カード（「最大 n 分流そうとしています」）で聞いてから、その分まで流す。30 秒で止まったら、`timeout_minutes` を付けて頼み直すよう失敗の文で伝える）。チャットの作業を止めたら（実行の `signal`）SQL も止める（承認を待つ間に止めていたら流さない）→ ワーカーの `export`（`worker/csvExport.ts` の `exportQuery`。ドライバの `stream` で行の数の上限なしに 1 行ずつ受け、`DB_AI_MAX_ROWS`（100）行を超えたときだけ CSV のファイルを作って頭の行から全部を書く（メモリに全部を持たない。PostgreSQL はカーソルで 1000 行ずつ、MySQL は流れてくるまま、SQLite は `iterate`。1 行目は列の名前・NULL は空・バイナリは `\x` と 16 進のすべて・ファイルは 0600。失敗・止めたら書きかけを消す））→ AI には頭の 100 行と、超えたら全体の行数と CSV の場所を返す（2026-11-11 に決めた。前は 30 秒・100 行で固定）。CSV の置き場所は `aiExports.ts`（OS の一時フォルダの `<保存先の名前>-db/<チャット>/<日時>-<接続の名前>-<印>.csv`。Kickoff の保存先は AI - compose の設定は compose 自身に聞く（YAML は読まない）: `docker compose -f … --profile '*' config --format json`（組の名前・サービス・札・published）と、作ってあるものだけ `config --hash '*'`（コンテナのラベルの指紋と比べて `config_changed`）。`ComposeConfigCache` が -f のファイルとそのフォルダの .env の更新日時を鍵に覚え、［↻］（`?refresh=1`）で捨てる。読めなければその見出しに `config_error` と、すべて起動を押せない理由 `start_blocked`。up に渡すファイルは、作ってあればラベルの config_files、作っていなければ `upFilesFor`（.env の `COMPOSE_FILE` に見つけたファイルがあればその並び、なければ決まった名前にだけ同じ系統の override を足す）。
- 操作（`POST …/docker/actions`。本文 `DockerActionBody`）: コマンドの並びは純粋な `actions.ts` の `planDockerAction`（すべて起動 = 作ってあるものは `compose -p <名前> start <札なしのサービス…>`、作っていないものだけ `up -d --no-deps`、何も作っていなければ `up -d`／停止・再起動・片付けは -p だけで `/` から流す（ファイルのあるフォルダで流すと札付きが残るため）／片付けは使い捨てを `rm -f` してから `down`（`-v` は付けない）／サービスの行はコンテナの ID（作っていなければそのサービスだけ up、札付きは `--profile`）／同じ作業場所のほかの compose と同じ組なら停止・再起動は ID で、片付けは断る）。compose ごとに 1 つずつ（動いていれば 409。一覧を取り直す前に「予約中」として覚え（`DockerService` の `reserved`）、取り直す間に届いた 2 つ目も 409 にする。始めたら・断ったら外す）、待たずに始めて 202 と始めたあとの一覧（cancel・dismiss は 204）、始まり・終わり・失敗のたびに SSE の `docker_changed`。up は時間で打ち切らず［中止］（`cancel`）で止める。失敗は標準エラーの最後の 8 行と［ターミナルで流し直す］のコマンドを、次の操作か［×］（`dismiss`）まで残す（DB に書かない）。up の経路は、同じ組の名前で別の場所（ほかの作業場所・ほかのプロジェクト・同じ作業場所のほかの見出し）のコンテナがあれば（`sharedVictims`）、`confirm_shared` がない限り 409 と `code: "docker_shared_project"`（画面が確かめて送り直す）。同じ組の名前の相手は一覧の `shares`（⚠）に出し続ける。
- ポートの取り合い（`portConflict.ts` の純粋な関数・`ports.ts`）: up の失敗の標準エラーからぶつかったポート（`allocatedPortOf`。「Bind for …:5432 failed: port is already allocated」と、Docker の外が先に待っていたときの「…:5432: bind: address already in use」）を読み、そのサービス（すべて起動なら札なしのサービス。`startedServices`）の published と同じポートを出している、この compose のものでない動いているコンテナを全部（`portConflictsOf`）、説明（`conflictLabel`: 「本体 | main の db」「WT | feat-x の db」「other（ほかのプロジェクト）の db」「name（compose の外で作ったコンテナ）」）付きで失敗の `conflicts` に残す。［相手を止めて起動］（`stop_others_and_start`。相手がなければ 400）は `planDockerAction` の `retry`（最後の失敗）から、相手を `docker stop` → 元の操作で起動しようとしたサービス（`actions.ts` の `startedServices`: 行ならそのサービス（札付きの行ならその札付き）、すべて起動なら札のないもの。相手の探し方と同じ決まり）のうちぶつかったものを `up -d --no-deps --force-recreate`（札付きは `--profile`。すべて起動から同じポートの札付きまで起動すると、今度はそれと取り合うため）→ 1 つのサービスの操作でなければ元の操作をやり直す。作り直すのは、ポートで起動に失敗したコンテナはあとで起動しても Mac にポートを出さないため（止め直しても戻らない。2026-11-13 に OrbStack で確かめた）。やり直しも失敗したら元の操作として残す。サービスを指した `recreate` もそのサービスだけ `--force-recreate`（画面の「ポートを出していません」の［作り直す］）。静かなぶつかり（Docker の外のプロセスが同じポートを待つ。localhost への接続がそちらに行く）は、一覧のたびに動いているこのプロジェクトのコンテナのポートで `lsof -nP +c 0 -iTCP -sTCP:LISTEN`（1 回。何もなければ終了コード 1）を読み（`parseLsof`。名前の `\xNN` を戻す）、同じポートを PID で 2 つ以上が待ち、Docker のエンジン（`DOCKER_ENGINE_PROCESSES`）でないものを一覧の `silent`（コンテナの ID ごと）に出す（`silentConflictsOf`）。ぶつかりがあるときだけ `brew services info --all --json` を聞き（30 秒覚える）、Homebrew のサービスなら名前を添える。`POST …/docker/brew-stop`（本文 `DockerBrewStopBody`。いまの `silent` にある名前だけ）が `brew services stop` を流して戻すコマンドの文を返す。コマンドは `PortProbe`（テストでは `setup()` の `portsFake`）。
- docker events（`events.ts` の `DockerEvents`）: 画面が `POST …/docker/watch` を 20 秒ごとに送る貸し出し（応答は今の一覧）。どこからも 45 秒届かなければ止める。変化は 300ms まとめて、見ているプロジェクトに `docker_changed`。events が終わったら（エンジンが止まった）知らせてから 5 秒ごとに調べ、戻ったら知らせて立て直す（調べ直す間隔と時計はテストで差し替える。`docker/events.test.ts`）。コアを閉じるときは止める（流している up は `stopAllStreams`）。
- ログの画面（`GET …/docker/logs?compose=<見出しのキー>`。SSE で `DockerLogEvent`）: `logs.ts` の `DockerLogSession` が、compose のコンテナ（`listing.ts` の `logSourcesOf`: 札 = サービス名、数を増やしたものは `svc#n`、使い捨ては「svc · 使い捨て」）ごとに `docker logs -f --timestamps --tail 500`（流れ続けるので `stream`）を立て、行を 100ms まとめて `lines` で送る。docker logs はコンテナの標準エラーを自分の標準エラーに出す（postgres などは普段のログも標準エラー）ので、両方を 1 行ずつ受ける。時刻は `parse.ts` の `parseLogLine` で小数 9 桁にそろえる（文字のまま比べて並べる）。そのプロジェクトの `docker_changed` と追っていたものが終わったときに `sync` で一覧を取り直し（重なった頼みは 1 つずつ）、止まったら `stopped`（終了コード）、同じコンテナが動き直したら `started` を送って受け取った最後の時刻から `--since` で続ける（`--since` は同じ時刻の行も返すので、追い始めたときの最後の時刻までは落とす）。作り直した・新しいコンテナは最新の 500 行から（作り直されたもの = 前に同じ札の別のコンテナを見ていたものは、`started` の区切りも送る。初めて開いたときは送らない）、止まっているものは最後の 500 行を 1 回だけ読む。何も作っていない compose（コンテナ 0 個）でもつながり、あとから作られたコンテナを `sync` で最新の 500 行から流し始める（画面は作っていなくても［ログ］を開ける）。画面を閉じたら（`onAbort`）流しているものをすべて止める。ログは保存しない。「さらに前を読む」は `GET …/docker/logs/before?compose=&container=&until=`（`DockerService.logsBefore`: その compose のコンテナでなければ 404、`--until` と `--tail 500` で読み、until と同じ時刻の行は落とす。`{ lines }`）。
- AI の守りが見る様子（`guardFacts.ts` の `createDockerGuard`。判定は `chat/guard/dockerGuard.ts`、決まりは `chat/CLAUDE.md` の「書き込みの守り」）: チャットの実行ごとに作り（`turn.ts` の `buildTurnParams` が `ProviderTurnParams.dockerGuard` に入れる。`ExecutionDeps.docker`）、docker の文があるときだけ問い合わせる。作業場所は `DockerService.workplacesOf`、`docker ps -a`（`PS_FORMAT`。working_dir は realpath）、compose の組の名前（そのコマンドの -f などと流す場所・行頭の環境変数で `compose … config --format json`。`DockerCli.run` の `env`）、ボリュームとその組のラベル（`volume ls`）、作業場所ごとの compose が答える組の名前（`DockerService.composeNames`。一覧と同じ `upFilesFor` で読む）。どれも 3 秒で打ち切り、答えなければ通す側に倒す。
- 「DB で開く」（段階 2。`GET …/docker/db?compose=&service=` → `DockerDbTarget`）: `DockerService.dbCandidate` がその見出しの up に渡すファイルの compose の設定（`ComposeRead.doc` = `config --format json` を読んだもの）から、純粋な `dbTarget.ts` の `dockerDbCandidate` で DB クライアントの取り込みと同じ案（`candidatesFromCompose`。localhost と Mac に出したポート・パスワードは environment から）を作る。ports がなければ押せない理由 `DOCKER_DB_NO_PORT`、DB のイメージでなければ 400。ワークツリーの db は本体の同じファイル・同じサービスの published と比べ、別のポートなら名前にブランチ（なければフォルダ名）を添える。登録済みの同じ DB（`sameServerConnection`: 種類・この Mac の中のホスト・ポート（書いていなければ既定のポート）。DB の名前まで同じものを先に）があればその `connection_id`、なければ案（`toImportCandidates`。パスワードは `has_password` だけ）。案の key は `docker:<サービス>:<見出しのキー>`（`dockerDbKey` / `parseDockerDbKey`）で、`POST …/db-connections/import` はこの key を compose に聞き直して作る（ポートを出していなければ 400）。ワークツリーを消しても、その db の接続は消さない（未決）。
- 口はどれも `localOnly`（この Mac からだけ）。テストは `server.docker.test.ts`・`server.dockerDb.test.ts`（「DB で開く」）・`docker/dbTarget.test.ts`・`docker/parse.test.ts`・`listing.test.ts`・`actions.test.ts`・`portConflict.test.ts`・`compose.test.ts`（compose のファイルの探し方・up に渡すファイル・設定を覚える口）（守りは `chat/guard/dockerCommand.test.ts`・`dockerGuard.test.ts`）。
